# DocWeave 0.1.0-beta.18

## Release status

State: **proposed full-library release**. Publication is not yet confirmed. The release automation will verify the
exact public source, create annotated tag `v0.1.0-beta.18` and a matching GitHub prerelease, and publish only a fresh
version after its checks pass. Previous public release: 0.1.0-beta.13. Versions beta.14 through beta.17 were internal
builds; this public release cumulatively includes their reviewed changes. Existing coordinates remain immutable.

The public release is independently built from public source. Internal artifacts are not substituted for Central
artifacts. This release does not change Studio's deployed images or internal library pin, or publish its separate SDK.

## Changes since public beta.13

### PDF memory and input ownership

PDFBox documents opened by the PDF module no longer retain image XObjects in the default resource cache. Fonts,
color spaces, forms and other resources keep their existing caching behavior. Application-supplied cache classes
or a disabled cache remain unchanged. This removes the document-length growth in decoded-image retention observed
on scanned PDFs; image references are decoded on each resolution, which can cost more for documents reusing images.

On the documented synthetic 200-page scans, under a 4 GiB heap, sampled peak heap fell from roughly 4 GiB to
1.0–1.3 GiB, with comparable post-GC live heap near 140 MiB. These are scoped measurements, not a universal memory
bound. Page resolution, OCR/layout state, native libraries, input/output and concurrent documents still consume
memory. See [measurements and limitations](../pdf-page-parallelism.md#memory-on-scanned-pdfs-010-beta15).

`DocumentSource.ownedBytes(byte[], String)` explicitly transfers ownership without copying. The caller must never
modify, reuse or expose the transferred array afterward. Public accessors still copy. `DocumentSource.bytes`
retains its defensive-copy contract; internal byte-source reads avoid an additional copy.

### Markdown

- List-item continuation blocks now belong to their list item rather than the enclosing heading.
- AST extraction records bold/italic contents, tags and code-point start offsets by default. Text and ordering are
  unchanged, but callers comparing whole metadata maps will see new keys.
- Six syntax extensions are opt-in and off by default: task lists, strikethrough, automatic links, footnotes,
  definition lists and front matter.
- Footnotes are numbered by reference order; AST modes keep definitions in document order and preserve omitted,
  duplicate and malformed note text. Headings within notes and definitions do not alter the surrounding outline.
  DOM extraction follows rendered HTML order and has documented text/metadata differences.
- Definition lists link terms and definitions through metadata. Front matter supports a bounded data-only subset:
  strings/lists, no object construction, tags, aliases or nested mappings. Values are attached to emitted elements;
  malformed recognized blocks remain text with a diagnostic.
- An owned corpus is qualified against a separately pinned Unstructured 0.27.37 reference. This is scoped
  qualification, not a claim of full dialect or quality parity.

```java
var options = PartitionOptions.builder()
        .markdownOptions(MarkdownOptions.defaults().withExtensions(java.util.EnumSet.of(
                MarkdownOptions.Extension.FOOTNOTES,
                MarkdownOptions.Extension.DEFINITION_LISTS,
                MarkdownOptions.Extension.FRONT_MATTER)))
        .build();
var result = DocWeave.create().partition(DocumentSource.text(markdown, "notes.md"), options);
```

See [Markdown contracts, modes and limitations](../markdown-support.md).

### Streaming JSON and PDF range APIs

`ElementJson` can write individual elements to a caller's JSON generator or output stream without buffering an
entire element list. PDF APIs add explicit contiguous page ranges, reusable prepared documents, per-page budget
accounting, range counting, assembly and a versioned range-result JSON codec. Whole-document extraction retains its
existing defaults and ordered output. Range results must match source/options and assembly contracts; distributing
ranges safely requires application-level coordination and budgets. These library APIs do not enable Studio
multi-VM distribution.

## Usage and upgrade

```xml
<dependency>
    <groupId>io.docweave</groupId>
    <artifactId>docweave-pdf</artifactId>
    <version>0.1.0-beta.18</version>
</dependency>
```

- Java 21 or later, no preview features; align all DocWeave modules to beta.18.
- `MarkdownOptions` now has an extensions component. The old four-argument constructor remains, but record patterns
  must include the additional component.
- `DocumentSource.OwnedBytes` adds a subtype to the sealed source hierarchy. Exhaustive consumer switches must
  handle it or provide a default; rebuild consumers against the updated API.
- Custom `ElementJson` implementations inherit new streaming methods that throw `UnsupportedOperationException`
  unless implemented. The built-in codec supplies them.
- Existing/default Markdown workflows do not enable syntax extensions automatically. Emphasis metadata and corrected
  list parentage are observable differences from public beta.13.
- Additional CommonMark extension dependencies and their license notices are recorded in the POMs and
  `THIRD_PARTY_NOTICES.md`; there is no YAML parser dependency.
- OCR, ONNX and S3 remain separate optional modules with explicit configuration. No engine/model is downloaded or
  enabled automatically. Earlier [beta.12 breaking changes](0.1.0-beta.12.md#usage-and-upgrade) still apply when
  upgrading from older public versions.

## Known limitations

PDF reading order, table recognition and OCR retain the limitations in [PDF support](../pdf-support.md). The memory
measurements do not establish a universal ceiling or unchanged speed on every PDF; repeated image decoding trades
cache retention for work. Caller-owned input mutation violates the ownership-transfer contract. Markdown modes
have documented differences, and front matter is intentionally not general YAML. Compatible-S3 testing is not AWS
qualification; Native Image is not qualified. Preserve documented resource limits and cancellation requirements.
