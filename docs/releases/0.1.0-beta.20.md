# DocWeave 0.1.0-beta.20

## Release status

State: **release candidate; not yet published to Maven Central**. Previous public release: **0.1.0-beta.18**.
This full-library release includes the changes qualified in internal-only beta.19. Existing published coordinates,
artifacts and tags remain immutable. The library targets Java 21 and runs on Java 21 or later.

## Changes since beta.18

### Standalone image OCR

The new `docweave-image` module partitions PNG, JPEG/JFIF and TIFF, including multi-page TIFF, using an explicitly
configured OCR provider. It is also included in the `docweave` convenience artifact. Image text extraction is
separate from PDF parsing; the same `PdfOcrProvider` can serve both.

- Content signatures identify PNG, JPEG and TIFF; a conflicting filename produces `FORMAT_MISMATCH`.
- JPEG EXIF and per-page TIFF orientation are applied before OCR, including mirrored orientations.
- Each recognized line becomes an `UncategorizedText` element with a page number and upright pixel coordinates.
- TIFF pages are processed in directory order, one decoded page at a time. Page and pixel limits are checked before
  decoding; malformed strip/tile extents and cyclic directory chains are rejected.
- A page with no recognized text produces `IMAGE_NO_TEXT` rather than invented text.

```xml
<dependency>
    <groupId>io.docweave</groupId>
    <artifactId>docweave-image</artifactId>
    <version>0.1.0-beta.20</version>
</dependency>
```

For real OCR, add `docweave-ocr-tesseract` at the same version and install Tesseract and the language data separately:

```java
var ocr = io.docweave.ocr.TesseractOcr.create(io.docweave.ocr.TesseractOptions.defaults());
var registry = io.docweave.partition.PartitionerRegistry.builder();
io.docweave.partition.ImagePartitioner.createAll(io.docweave.partition.ImageOptions.defaults(), ocr)
        .forEach(registry::register);
var result = io.docweave.DocWeave.create(registry.build()).partition(java.nio.file.Path.of("scan.tiff"));
```

See [image support](../image-support.md) for configuration, metadata, limits and the scoped comparison with
Unstructured 0.27.28.

### DOCX input memory

The DOCX archive verifier and POI now read streams over the existing read-only input buffer instead of making a
complete defensive copy through `PartitionContext.binaryContent()`. This removes one full-input copy. Extracted
output is unchanged. POI still expands package parts within the existing DOCX limits; this is not a constant-memory
DOCX parser.

## Upgrade impact

- Upgrade all DocWeave modules together to beta.20; Java package names remain `io.docweave`.
- `DocumentFormat` gains `PNG`, `JPEG` and `TIFF`. Consumers with exhaustive enum switches may need additional cases.
- The convenience artifact now discovers image partitioners. Their service-loaded defaults have no OCR provider;
  image extraction fails explicitly with `UNSUPPORTED_OPTION` until a provider is configured.
- No OCR executable, language data or model is downloaded automatically. Optional OCR/layout adapters remain
  separately configured. Text extraction from existing document formats keeps its previous behavior.
- This library release does not deploy Studio, publish the Studio SDK, or change saved workflows or model settings.

## Validation

The image implementation and DOCX fix were reviewed and qualified before this public candidate. The internal
beta.19 build passed the full Java 21 reactor; image acceptance with real Tesseract passed at 1 GiB and 256 MiB heap.
The committed [image evidence](../../benchmarks/review/image-upstream-0.27.28/README.md) records the fixture scope,
runtime versions and limits. These historical results do not substitute for the public candidate's verification.

The Maven Central release pipeline must independently pass full Java 21 verification, strict Javadoc, archive and
bytecode/license checks, and the standalone optional-adapter consumers before signing and uploading this candidate.
Its S3Mock helper uses Java 25; the library and test JVM baseline remains Java 21. Publication is confirmed only after
Central reports success and the published artifacts match the canonical candidate hashes.

## Known limitations

Image partitioning extracts OCR text only: no captioning, visual question answering, table detection or layout model.
BigTIFF is detected but unsupported. OCR quality depends on the configured provider and input quality. Cancellation
is cooperative; there is no deterministic bound for aborting an ImageIO decode already in progress. The OCR adapter
also creates an in-memory PNG representation of each page, and the external OCR process has its own memory usage.

Memory and comparison reports cover owned synthetic fixtures, not general extraction accuracy or a universal memory
bound. See the existing [PDF](../pdf-support.md) and [DOCX](../docx-comparison.md) contracts for unchanged limitations.
