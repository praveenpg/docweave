# Invisible Type3 glyph paint and table evidence

A real Type3 font can execute arbitrary drawing operators for a character. Rendering
mode3 (`NEITHER`) makes that glyph invisible, but the native graphics visitor previously
retained its stroked/filled grid as table evidence.

An owned native source reproduces the defect: an invisible grid glyph plus six ordinary
text labels produces one Table. Replacing the invisible glyph program with a nonpainting
program gives a byte-identical rendered page and no Table. The source text, encoding,
font matrix, label positions and page are otherwise fixed. Separate PDFBox rendering
establishes pixel equality of the two complete 240×280 page controls before extraction.
This is a constructed source counterexample, not a new real-world corpus accuracy score.

The correction scopes paint suppression to invisible Type3 glyph traversal. It excludes
stroked rules, filled-rule centerlines and shaded-row evidence. Visible Type3 programs
keep their own painting operators; ordinary-font rendering-mode semantics are not
substituted for Type3 drawing semantics. Normal page paint remains eligible after the
glyph even if the retained text state still has rendering mode3.

Source traversal remains active. Images remain source occurrences, and the shared
operator/cancellation checks still run. The parent suppression state is restored in
`finally`, including after cancellation and operator exhaustion. No public option,
provider dependency, text-selection default, font substitution or threshold changes.
This does not implement general clipping, optional-content visibility or page compositing.

## Java21 verification

Five new JVM methods cover the public render-equivalent false-table case and positive
visible-table control; ordinary page paint after an invisible glyph; filled and combined
glyph paint; retained source images; and cancellation/budget unwinding. The original
red control emitted one false table; the corrected result emits none, while the positive
visible/ordinary-page controls each retain one table.

The focused Type3/form/stroke/fill/image suite passes 22 methods. Full Java21 verification
passes **1,274 tests, zero failures/errors/skips**, strict public Javadocs and standalone-source
compilation. Two-file strict private Javadocs, scoped formatting and diff checks pass.
`java21.json` records numeric outcomes and source/log hashes. Raw authored sources are
generated by the tests; no external font, PDF, OCR engine or model is required.

No published artifact, public-source synchronization or general document-quality gain
is implied by these development results. Java25 verification remains reserved for final
PDF acceptance or a release candidate.
