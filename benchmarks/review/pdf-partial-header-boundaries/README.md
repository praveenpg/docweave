# Partial-table header column recovery

The known six-page `us-020.pdf` statistics original improves from 339/350 to **350/350**
saved CSV positions under the explicit `RULED_AND_PARTIAL_TEXT` policy. All 11 gains are
header positions: 24/35 becomes 35/35; body positions stay 315/315. The sole selected-page
table remains 50 by 7 with exactly the same parent coordinates. No source/reference text,
row population, crop, numeric parsing or normalization rules change.

The previous generic line grouper joined adjacent header headings across supported
column boundaries when their source gap was less than 12 PDF units. Header grouping now
splits where an existing column boundary falls inside a source gap greater than twice
the larger reported space width (and at least one unit). This rule uses source geometry,
not reference strings. Ordinary word spaces and continuous spanning titles retain their
previous grouping. It is an explicit-policy heuristic, not a semantic header oracle;
deliberately widely spaced titles can remain ambiguous. Default and other policies are unchanged.

## Evidence

An owned regression places two headings on opposite sides of a supported boundary with
a gap below 12 units. Before the fix they become a spurious spanning cell; after it they
remain separate. The genuine three-column title stays a spanning anchor. Existing fallback,
geometry, work/cancellation, caller limits and concurrent service controls pass (8 methods).

The JVM evaluator processes the complete pinned PDF before loading its CSV reference.
It verifies both SHA256 identities, the full 50-by-7 population and anchor topology, then
projects anchors once. Covered positions are blank; absent slots receive no empty-cell
credit. Only ASCII whitespace collapses; Unicode/case/punctuation are preserved, with
built-in ASCII/NBSP controls. References remain saved native extraction expectations,
not independently reviewed physical spans or scan transcriptions.

[Baseline](baseline-java21.json) and [candidate](candidate-java21.json) are generated by
[the same retained JVM scorer](../../tools/VerifyPartialHeaderReference.java). The baseline
uses the detector from development parent `1cc629d`, compiled into an isolated first
classpath entry; it reproduces the historical 339 result. Candidate uses current classes.
All source/reference pins come from the unchanged
[business manifest](../pdf-business-cell-text/manifest.json). No source-dependent policy
routing or reference text enters production.

Whole-original captures of all three retained documents under all six native policies
retain all 18 successful case/profile observations. Only statistics/partial changes;
all other case/profile records and source-frame records are recursively equal. Raw HTML,
source text and captures remain outside Git. The financial and procurement gaps remain.

Full Java 21 verification passes 1,283 tests with zero failures/errors/skips. Changed
production/test/tool sources pass private strict Javadocs and scoped formatting. Final
standalone-source compilation passes after evaluator formatting/normalization controls.
No Java 25, OCR/model execution, new library dependency or broad PDF gate closure is claimed.

## Reproduction

Compile `VerifyPartialHeaderReference.java` with the existing Java 21 validation classpath,
including core/PDF, Commons CSV, jsoup and Jackson already used by the project tools.
Run with the original cache and a fresh numeric report:

```sh
java -cp "$probe_classes:$validation_classpath" VerifyPartialHeaderReference \
  /path/to/original-cache /path/to/fresh-report.json
```

The source cache must contain the exact pinned `us-020.pdf` and `us-020.csv`. To reproduce
the baseline, compile the parent detector source into an isolated directory and place it
before current classes. Do not overwrite current or historical artifacts. Numeric results
and source identities are recorded in [the receipt](java21.json).
